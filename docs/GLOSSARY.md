# Project Glossary & Domain Terminology

> **Document Status:** Phase 0 Baseline — Frozen  
> **Last Updated:** 2026-10-09  
> **Document Owner:** Architecture Team  

---

This glossary provides authoritative, canonical definitions for all core domain concepts, entities, and architectural terminology used across the **Meeting Recording Summarizer** codebase, documentation, and tests.

---

## 1. Domain Entities & Concepts

### User
The authenticated identity owning workspaces, meetings, recordings, transcripts, and intelligence data. Represented by a UUID matching the authentication provider's subject claim (`sub`).

### Meeting
The logical parent container representing a specific discussion or event. A meeting owns exactly one `Recording` (in MVP), one or more `ProcessingJob` runs, one `Transcript`, one `MeetingAnalysis`, and optionally future `ChatSession` instances.

### Recording
The media binary (audio or video) associated with a Meeting. Stored exclusively in private object storage (e.g. Cloudflare R2), referenced by a secure storage key, and tracked with lifecycle metadata (size, duration, format, status).

### Transcript
The structured text output resulting from the speech-to-text transcription of a Recording. It is the authoritative textual representation of the meeting dialogue and owns an ordered collection of `TranscriptSegment` records.

### TranscriptSegment
A single atomic, timestamped utterance in a Transcript. Stored as an individual relational record containing `id`, `transcript_id`, `sequence_index`, `start_time` (seconds), `end_time` (seconds), `speaker_label` (e.g. `SPEAKER_00`), `speaker` (user-mapped name or NULL), `text`, and optional `metadata`. It serves as the canonical source for all timestamp calculations and evidence citations.

### ProcessingJob
An asynchronous unit of work executed by a background Worker process. It transitions through explicit domain statuses (`PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `CANCELLED`) and sequential stages (`VALIDATING`, `EXTRACTING_AUDIO`, `TRANSCRIBING`, `DIARIZING`, `ANALYZING`, `VERIFYING`, `SAVING`). It tracks `celery_task_id`, worker lease metadata, attempt counts, execution duration, and error codes in PostgreSQL.

### Worker
An independent background runtime process (separate runtime container from the FastAPI HTTP API) running Celery worker processes with late acknowledgements (`acks_late=True`) and fair task prefetching (`prefetch_multiplier=1`). Responsible for executing audio extraction, transcription, diarization, and LLM analysis, renewing job leases via periodic heartbeats in PostgreSQL, and persisting outcomes.

### Celery & Redis
- **Celery:** Distributed asynchronous task queue framework in Python that handles worker scheduling, concurrency, task retries, and loss rejection (`reject_on_worker_lost=True`).
- **Redis:** High-performance in-memory data store functioning as the task broker transporting asynchronous Celery tasks between the FastAPI API and Celery workers. PostgreSQL remains the authoritative durable source of truth.

### Speaker Diarization, Speaker Label & Participant Name
- **Speaker Diarization:** The process of partitioning an audio recording into homogeneous segments according to speaker identity ("who spoke when"), implemented via pyannote Community-1.
- **Speaker Label:** Machine-assigned anonymous identifier (e.g., `SPEAKER_00`, `SPEAKER_01`) generated by the diarization model.
- **Participant Name:** Human-friendly display name (e.g., "Alice") assigned by the user and mapped to a speaker label in `meetings.speaker_mappings`.

### Targeted Verification
A selective secondary LLM reasoning call invoked only when deterministic validation detects an ambiguous, ungrounded, or high-impact claim, avoiding the latency and financial cost of running a blanket second "critic LLM" on every routine meeting.

### FFmpeg
Open-source audio and video processing engine used in the worker container to inspect media headers, validate audio streams, extract audio tracks from video recordings, and normalize audio to standard 16 kHz mono WAV prior to transcription and diarization.

### Analysis (MeetingAnalysis)
The synthesized structured intelligence derived from the Transcript by the `MeetingAnalysisAgent`. Contains executive summary, topics, decisions, action items, risks, and open questions.

### MeetingAnalysisAgent
The bounded AI reasoning component responsible for extracting structured intelligence from timestamped transcript segments (using Groq GPT-OSS 120B / 20B). It operates strictly on provided text without inventing missing facts, owners, or dates.

### Evidence
A direct citation mechanism linking an extracted intelligence item (decision, action item, risk, open question) to one or more `TranscriptSegment` UUIDs (`evidence_segment_ids`). Enables users and verification tests to trace every insight directly back to the verbatim source conversation.

### Decision
A clear, explicit agreement, choice, or consensus arrived at during the meeting, linked to source transcript segments.

### ActionItem
A concrete task, follow-up, or commitment made during the meeting. Consists of a description, an optional owner (set to `null` if not stated verbatim), an optional due date (set to `null` if not stated verbatim), and supporting `evidence_segment_ids`.

### Risk
A highlighted issue, blocker, hazard, or concern explicitly raised in the discussion, with supporting `evidence_segment_ids`.

### OpenQuestion
An unresolved question or inquiry identified during the discussion that requires future clarification, with supporting `evidence_segment_ids`.

### ChatSession & ChatMessage
Planned interactive conversational entities enabling post-analysis natural language Q&A against a meeting's transcript and intelligence. Designed to be introduced cleanly without disrupting the core data model.

## 2. Infrastructure & Architectural Terminology

### Provider
An abstract software boundary encapsulating external third-party services behind standardized Python abstract base classes (`ABC`). Prevents vendor lock-in and decouples application logic from external SDKs.

### LLMProvider
An interface defining completion and structured generation methods for Large Language Models (e.g., `GroqProvider` for GPT-OSS 120B/20B, `OpenAIProvider`, `MockProvider`).

### TranscriptionProvider
An interface defining speech-to-text transcription methods for audio files (e.g., `GroqWhisperProvider` for Whisper Large V3 Turbo, `LocalWhisperProvider` for dev, `MockTranscriptionProvider`).

### StorageProvider
An interface defining private object storage operations (e.g., `R2StorageProvider`, `S3StorageProvider`), including generating pre-signed `PUT` upload authorizations and pre-signed temporary `GET` read URLs.

### Job Lease & Heartbeat
A concurrency control and failure detection mechanism where a Worker claims a job in PostgreSQL by populating `worker_id`, `claimed_at`, and `lease_expires_at`. The worker periodically issues heartbeats (`heartbeat_at`) to extend the lease during long-running tasks. If a worker container crashes, expired leases allow subsequent workers to reclaim the job safely.

### Idempotency
The property whereby executing a job or processing step multiple times produces the same final system state without duplicating records or corrupting data.

### Retry & Exponential Backoff
A systematic reliability pattern wherein transient failures (network timeouts, rate limits) trigger automated re-attempts with progressively increasing delay intervals up to a maximum attempt threshold.
